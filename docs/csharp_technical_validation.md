# C# 无障碍路线技术验证目标

## 目的

本文件定义将 C# 作为后续无障碍功能主开发路线之前，必须完成的技术验证。

当前已发布实现基于 `UE4SS + Lua + C++ Tolk bridge`。该实现可以完成部分菜单聚焦文本朗读，但功能扩展依赖 Unreal 反射可见对象与具体控件树结构。对于战斗状态、交互目标、导航和复杂界面语义，继续扩大基于 WidgetTree 的适配范围，维护成本和失效风险都较高。

C# 路线通过 `B1CSharpLoader` 进入游戏托管环境，并直接引用游戏程序集。其预期价值是从游戏业务对象和事件获取语义信息，而不是从最终显示控件反推信息。本文件只验证该预期是否成立，不预先决定整体迁移。

## 验证结论门槛

满足以下条件后，才可将新增大型功能默认转向 C#：

- C# mod 能独立完成屏幕阅读器输出，不依赖 Lua mod 承担输出链路。
- C# 能从游戏业务 API 或事件获得至少一种玩家状态变化与一种实时事件。
- C# 能覆盖至少一个现有 UI 朗读场景，或明确证明该场景应保留为 UE4SS 补充能力。
- Loader、Harmony hook 和输出链路在实际游戏运行中具有可接受的稳定性。
- 发布包可以完整安装并运行 C# mod，而不仅是安装 Loader。

在上述门槛完成前，UE4SS 版本仍是现有可用功能的发布基线，C# 代码仅视为技术验证。

## 技术假设

### UE4SS 路线现状

- UE4SS 可以 hook 反射可见的 `UFunction`，也可以监听反射可见 `UClass` 的对象构造。
- 当前项目实际使用入口是 `BUI_Button:OnAddedToFocusPath`，随后从聚焦控件遍历父子 WidgetTree 取得文本。
- 此方式适用于少量已有菜单适配，但不能自然提供血量变化、技能状态、受击、锁定目标或导航信息。
- 将 Lua 改为 UE4SS C++ 可以改善编码质量，但不能自动突破游戏业务语义不可见的问题。

### C# 路线预期

- `B1CSharpLoader` 可以加载实现 `ICSharpMod` 的 C# 程序集。
- C# 可引用 `b1.Managed.dll`、`B1UI_GSE.Script.dll`、`UnrealEngine.dll` 等游戏程序集。
- Harmony 可以针对托管方法或事件入口建立补丁。
- 已有验证代码能够获得玩家对象并读取 `Hp` / `HpMax`，但尚未形成无障碍输出能力。

### 已知风险

- `B1CSharpLoader` 依赖代理 DLL 注入和运行时字节签名；游戏更新可能导致加载失败。
- 为支持 hook 而启用 JIT 可能影响稳定性、性能或其他 mod 的兼容性。
- 游戏托管 API 仍可能未暴露所有 UMG、Slate 或原生 Unreal 数据。
- Harmony 补丁若选择过高频事件，可能导致性能问题或过量朗读。

## 验证阶段

### V0：可复现的开发与安装环境

**目标**

建立可重复构建、安装、启动与收集日志的 C# 验证环境。

**验证内容**

- 编译 `csharp/WkAccess/WkAccess.csproj`。
- 将 `WkAccess.dll` 安装到 `CSharpLoader/Mods/WkAccess/`。
- 确认 Loader 启动后执行 `WkAccess.Init()`。
- 记录使用的游戏版本、Loader 版本、`EnableJit` 设置与日志位置。

**通过标准**

- 从干净安装目录开始，可依据文档重复完成安装并在日志中看到 `WkAccess Init()`。
- 发布测试目录包含实际 mod DLL，而不是只有 `version.dll` 和 Loader 依赖。

### V1：屏幕阅读器输出闭环

**目标**

确认 C# 可以独立输出可访问文本，为后续功能提供统一输出通道。

**验证内容**

- 在 C# 中封装 `Tolk` 输出适配器。
- 优先验证 `Tolk_Output`，同时记录 `Tolk_Speak` 的行为差异。
- 支持中文、英文、打断当前输出和无后端时的错误处理。
- 用固定快捷键触发验证朗读，不依赖 UI hook。

**通过标准**

- NVDA 及至少一种项目计划支持的其他读屏软件能够接收中文朗读。
- 无读屏后端或 DLL 加载失败时，mod 不崩溃，并输出可定位的日志。
- 后续模块仅通过统一输出接口请求播报，不直接调用 Tolk。

### V2：玩家状态读取

**目标**

证明 C# 可以直接读取无障碍所需的业务状态，而不是解析 HUD。

**验证内容**

- 获取当前受控角色。
- 读取生命、法力或气力、棍势等可用属性。
- 验证角色不存在、切换地图、死亡或重新载入后的对象生命周期处理。
- 提供手动查询朗读，用于验证数值准确性。

**通过标准**

- 至少可靠读取并朗读生命值与最大生命值。
- 数据来自游戏状态 API，而不是界面文本控件。
- 切换场景或重新进入游戏后，不因保存失效对象引用而崩溃。

### V3：状态变化事件与播报策略

**目标**

证明核心功能能够事件驱动运行，并验证高频信息的可用播报策略。

**验证内容**

- 挂钩至少一种真实变化事件，例如属性变化、受击或锁定变化。
- 将事件转换为无障碍语义，例如“生命低于百分之三十”或“受到重击”。
- 实现最小的去重、节流、优先级和打断策略。
- 记录 hook 调用频率与朗读数量。

**通过标准**

- 无需轮询 HUD 或等待焦点变化即可播报至少一种运行时变化。
- 连续战斗情况下不会因重复事件形成不可用的语音轰炸。
- 性能与稳定性没有出现明显回归。

### V4：UI 语义访问能力

**目标**

判断 C# 是否能够替代现有 Lua WidgetTree 解析，覆盖菜单朗读场景。

**验证内容**

- 选择一个已被 UE4SS 版本覆盖的界面作为对照，优先选择设置菜单或主菜单。
- 寻找对应的托管 UI 类型、数据模型、选中项变化事件或可读取文本属性。
- 实现焦点或选项变化后的朗读。
- 对比 C# 获取文本所依赖的对象层级与 Lua 现有适配器复杂度。

**通过标准**

- C# 至少覆盖一个真实菜单交互场景，并能朗读名称与当前值或描述。
- 若无法直接获得语义，必须记录阻碍边界：类型不存在、对象未加载、方法不可 patch，或仍只能遍历控件树。
- 依据结果决定 UI 朗读是迁移到 C#，还是保留有限的 UE4SS fallback。

### V5：目标功能可达性探针

**目标**

对计划中的大型功能逐项判断是否存在可靠的数据或事件入口。

**验证清单**

| 功能 | 需要验证的数据或事件 | 最低证明 |
| --- | --- | --- |
| 实时战斗状态 | 生命、气力、棍势、技能或 Buff 状态 | 找到稳定 API 或事件并朗读一次变化 |
| 敌人锁定提示 | 当前目标、锁定/解除、目标位置或距离 | 识别锁定变化并输出方向或距离之一 |
| 可交互物提示 | 当前交互对象、提示文本、进入/离开范围 | 在不读取屏幕文字的情况下识别一次交互对象 |
| 掉落/获得物品 | 奖励或背包变化事件、物品数据 | 输出一次实际获得内容 |
| 导航辅助 | 玩家位置、朝向、目标点或地图标记 | 计算并朗读到固定目标的相对方向 |

**通过标准**

- 至少两项大型功能找到业务层入口，其中至少一项来自战斗或导航领域。
- 未找到入口的功能明确记录为未知、不可达或需要混合技术方案，不能以 UI 推断结果代替验证。

### V6：运行稳定性与兼容性

**目标**

判断 C# 路线的底层风险是否低于其带来的功能收益。

**验证内容**

- 比较 `EnableJit` 开启与关闭时可用的 hook 能力和稳定性。
- 验证启动、载入存档、死亡重生、传送、长时间战斗和退出游戏。
- 验证与当前 UE4SS 发布版是否可以共存，仅用于过渡期评估。
- 对游戏更新后的失败表现进行记录：Loader 无法注入、类型或方法签名变化、Harmony patch 失败。

**通过标准**

- 关键验证流程内无稳定复现的崩溃或存档风险。
- 若必须开启 JIT，明确其必要性、兼容性影响与面向用户的风险告知。
- 日志能够区分加载失败、hook 失败、游戏 API 变化和输出后端失败。

## 验证产物

每个阶段应保留以下结果，避免只依据运行印象作路线决策：

- 验证代码及其对应的构建配置。
- 使用的游戏版本、Loader 版本与 mod 版本。
- 安装目录结构和必要依赖列表。
- 触发步骤、预期朗读、实际朗读和日志片段。
- 发现的 API、事件、类名和方法签名。
- 已知失败情况、崩溃条件与兼容性限制。

## 目标架构边界

C# 路线验证通过后，新的无障碍能力应按以下职责拆分：

```text
Game Integration
  - Player state source
  - Combat event source
  - Interaction source
  - Managed UI source

Accessibility Core
  - Semantic announcement model
  - Deduplication and throttling
  - Priority and interruption policy
  - Feature configuration

Output
  - Tolk adapter
  - Diagnostic logging
```

业务 hook 不应直接拼接并朗读文本；它们应先产生可测试的语义事件，再由播报策略与输出层处理。

## 路线决策

### 转向 C# 主线

当 `V0` 到 `V4` 全部通过，且 `V5` 至少验证两项大型功能可达时：

- 新增功能默认以 C# 实现。
- UE4SS 版本仅维护已有已发布能力，直到相应功能被 C# 稳定覆盖。
- 后续评估是否移除 UE4SS 运行依赖。

### 保持混合方案

当 C# 能可靠取得游戏状态与战斗事件，但无法合理读取部分菜单语义时：

- C# 承担状态、战斗、交互与导航能力。
- UE4SS 仅保留数量受控、已验证稳定的 UI 页面朗读。
- 不继续在 Lua 中扩展需要业务状态的新功能。

### 不采用 C# 主线

当以下任一情况持续存在且没有可接受解决方案时，不应将 C# 作为发布主线：

- Loader 或 JIT 导致不可接受的崩溃、性能或兼容性问题。
- 无法建立可靠的屏幕阅读器输出闭环。
- 关键游戏业务事件在 C# 中同样不可达。
- 游戏更新导致验证过的入口无法以可维护方式恢复。

## 首轮验证顺序

1. 完成 `V0`，修正 C# mod 的构建、安装和发布目录。
2. 完成 `V1`，在 C# 中接通 Tolk 输出。
3. 完成 `V2` 与 `V3`，优先验证生命值变化播报。
4. 完成 `V4`，用设置菜单与现有 Lua 版本作对照。
5. 完成 `V5`，优先调查锁定目标与交互对象。
6. 完成 `V6`，再作是否将 C# 提升为主线的最终判断。
