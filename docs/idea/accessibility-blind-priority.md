# 盲人玩家无障碍功能优先级排序

## —— 基于行业调研与现有 Mod 现状的专项分析

> **前置阅读**: [动作游戏无障碍功能研究报告](./accessibility-research-report.md)
>
> **背景**: 本报告针对《黑神话：悟空》无障碍 Mod (WkAccess) 项目，基于行业调研结论和现有代码实现现状，对功能进行针对盲人（完全失明，非低视力）玩家的重新优先级排序。

---

## 核心前提：盲人玩家的需求与通用无障碍的根本差异

通用无障碍指南（GAG / APX / XAG）以"第二通道"(Second Channel) 为核心原则——关键信息不得仅通过单一感官渠道传达。这个原则对盲人玩家而言不是"补充"而是"唯一的生命线"：**所有视觉信息必须转化为音频或触觉输出，否则对盲人玩家等价于不存在。**

这导致了优先级排序的根本性变化：

| 通用报告中的功能 | 通用优先级 | 盲人场景下的变化 |
|---|---|---|
| 颜色无关信息传达 | Basic（必备） | ❌ **不再适用** — 盲人玩家不依赖任何视觉信息 |
| 高对比度模式 | Intermediate | ❌ **不再适用** |
| UI/文本缩放 | Intermediate | ❌ **不再适用** |
| 字幕/说明文字 | Basic | ❌ **不再适用** — 字幕是视觉媒介，对盲人无用 |
| 屏幕阅读器 | Advanced | ⬆️ **升级为 T0** — 是所有其他功能的唯一输出渠道 |
| 攻击预警音频替代 | Basic | ⬆️ **升级为 T1** — 没有视觉预警，盲人战斗中完全被动 |
| 目标锁定辅助 | Advanced | ⬆️ **升级为 T1** — 没有视觉跟踪，无法找到/保持目标 |
| 导航辅助 | 未充分覆盖 | ⬆️ **升级为 T1** — 没有视觉探索，无法自主移动 |
| 音频描述（过场） | Advanced | ⬆️ **升级为 T3** — 剧情理解完全依赖此功能 |
| 连按→长按替代 | Intermediate | ➡️ **保持** — 与视力无关，操作无障碍仍然重要 |

**核心结论**：通用报告中的大量"视觉无障碍"功能对盲人玩家毫无意义；同时许多被通用报告列为 Advanced 的功能，对盲人玩家而言是**生存级必需**。

---

## 优先级分层框架

针对盲人玩家，采用五层优先级（与通用报告的三层完全不同）：

```
T0 — 前置阻塞：不实现则后续所有功能均无法生效
T1 — 核心生存：不实现则游戏完全不可玩
T2 — 战斗能力：不实现则战斗中完全被动
T3 — 探索能力：不实现则无法自主移动和探索
T4 — 完整体验：不实现则错过重要内容和便利性
```

---

## T0 — 前置阻塞（1 项）

> 不做这一步，后面所有功能都是纸上谈兵。

| # | 功能 | 当前状态 | 工作量估计 |
|---|---|---|---|
| **T0** | **真实 TTS 接入**：通过 Tolk P/Invoke 连接 NVDA / JAWS / SAPI 等屏幕阅读器 | ❌ `A11yTolk.Speak()` 仅输出日志；Tolk DLL 已存在于 `.cyhan/tolk-RelWithDebInfo-x64+0821/`，.NET 示例已存在，但 P/Invoke 包装未编写 | **小**（连接现有 DLL） |

**说明**：当前 Mod 的 4 个 TTS 调用点（UI 焦点朗读、交互物品朗读、F1 页面描述、输入提示朗读）的"朗读"内容实际上只写入日志文件，盲人玩家无法感知。Tolk 库已就绪，只需编写 C# P/Invoke 包装即可打通。这是所有后续功能的信息输出管道。

**为什么不是 T1**：代码层面是一个独立的小任务；但从功能依赖角度，T1–T4 的所有功能都依赖 T0 作为输出通道——所以说它"阻塞"后续所有功能。

---

## T1 — 核心生存（4 项）

> 不实现这些，盲人玩家打开游戏后处于完全黑暗且无声的状态，连"我在哪、我在做什么"都无法知晓。

### T1.1 玩家状态主动播报

| 属性 | 内容 |
|---|---|
| **功能** | 一键触发（或定时播报）当前玩家关键状态：HP、MP、耐力、葫芦剩余次数、当前棍势层数、异常状态 |
| **当前状态** | ❌ `Ctrl+Enter` 仅输出 HP 到日志，不朗读；无 MP/耐力/葫芦/棍势播报 |
| **调研依据** | GAG Basic — "关键状态信息不得仅通过视觉传达"；`idea.md` 中已列为待实现 |
| **实现难度** | **低** — `DebugCommands.PrintPlayerInfo` 已能读取 HP，需扩展读取 MP/耐力/葫芦次数等属性并触发 TTS |

**预期体验**：玩家按一个键，听到"生命值 85%，法力值 60%，耐力满，葫芦剩余 4 口，棍势一层"。

### T1.2 场景/地图自动播报

| 属性 | 内容 |
|---|---|
| **功能** | 场景切换时自动播报当前位置（场景名 + 区域名），玩家主动查询时播报当前所在区域描述 |
| **当前状态** | ⚠️ 部分实现 — `SceneMonitor` 已能检测场景切换（MainMenu / InGame / PauseMenu 等），`PageSpeaker.DescribeCurrentUI` 在 F1 时播报当前页面名。但缺少：自动触发（当前仅 F1 手动）、区域级别的位置描述、地图名播报 |
| **调研依据** | GoWR 的导航辅助系统提供音频提示描述周围环境；盲人玩家进入新场景后第一需求是"知道自己在哪" |
| **实现难度** | **低** — 扩展现有 `SceneMonitor` 即可，场景名已通过 `EnumLocale` 中文化 |

### T1.3 交互物品识别与引导

| 属性 | 内容 |
|---|---|
| **功能** | 靠近可交互物品时自动播报物品名和交互方式；提供朝向指引（如"土地庙在前方 3 米"） |
| **当前状态** | ⚠️ 部分实现 — `InteractMonitor` + `InteractSpeaker` 已能检测并播报交互目标（土地庙/宝箱/采集物/NPC 等 12 种），但只播报名称不播报距离和方向 |
| **调研依据** | GAG Basic — "可交互物品不得仅通过视觉高亮标识"；TLOU2 的 Enhanced Listen Mode 提供音频提示定位物品 |
| **实现难度** | **中** — 物品检测和名称已就绪，需补充：从玩家位置计算距离、从玩家朝向计算方向（时钟方位）、播报格式化 |

### T1.4 菜单/UI 完整朗读

| 属性 | 内容 |
|---|---|
| **功能** | 所有菜单页面（主菜单、设置、物品栏、装备、技能树、土地庙、商店等）的全部按钮/选项在焦点切换时自动朗读名称、值和状态 |
| **当前状态** | ⚠️ 已实现 40+ 控件类型的基础朗读，但：(1) TTS 仅日志、(2) 部分控件只能读值不能读名称、(3) 库存物品名称依赖间接解析偶尔退化为 `[??]` |
| **调研依据** | GAG Basic — "UI 信息不得仅通过视觉传达"；盲人管理装备/技能/物品的唯一途径 |
| **实现难度** | **中** — 主要工作是修复已实现的朗读链路（TTS 接入）、补充缺失的控件类型、修复 `[??]` fallback |

## T2 — 战斗能力（5 项）

> 不实现这些，盲人玩家进入战斗后完全被动——不知道敌人在哪、何时攻击、自己是否击中。

### T2.1 目标锁定辅助与播报

| 属性 | 内容 |
|---|---|
| **功能** | 辅助锁定最近敌人 → 播报"已锁定 [敌人名]，距离 [X] 米"；锁定丢失时自动重新锁定；锁定后自动朝向目标；播报敌人基本状态（血量等级感知） |
| **当前状态** | ❌ 完全未实现，代码库中无任何战斗锁定相关代码 |
| **调研依据** | TLOU2 的 Auto-Target 方案（自动锁定躯干、自动切换目标含屏幕外）；`idea.md` 中提及"怪物锁定音效"；研究报告中 A4（Advanced 级→盲人场景上升为 T2） |
| **实现难度** | **高** — 需要：(1) 获取玩家周围敌人列表、(2) 计算最近/最威胁敌人、(3) 模拟锁定输入或操作游戏内置锁定机制、(4) 持续监控锁定状态变化、(5) 读取敌人名称和血量进行播报 |

**为什么是 T2 而非 T1**：严格来说，盲人可以在没有锁定的情况下胡乱攻击（有 T2.2 攻击预警时也能被动闪避），但没有锁定就无法进行有效战斗。在"理论上可玩"和"实际上可玩"之间，锁定辅助是后者。

### T2.2 敌人攻击预警音频提示

| 属性 | 内容 |
|---|---|
| **功能** | 将敌人的攻击前摇/预警转化为有方向的音频提示（不同攻击类型不同音色：可格挡攻击/不可格挡攻击/范围攻击/远程攻击）+ 方向信息 |
| **当前状态** | ❌ 完全未实现 |
| **调研依据** | 研究报告 B1 级（Basic——方向性音频提示必须可视化替代，对盲人则是音频替代视觉预警）；GoWR 的音频提示词汇表概念可借鉴——不同声音类型对应不同信息类别 |
| **实现难度** | **很高** — 核心挑战：(1) 如何检测敌人即将攻击（动画事件？AI 状态？攻击判定框生成？）、(2) 如何判断攻击类型、(3) 如何计算攻击方向。这些信息可能在游戏引擎层面不暴露给 Mod 脚本。可能需要从动画通知、粒子特效事件或碰撞检测中推断 |

**技术风险**：这是整个盲人功能清单中**技术可行性最不确定**的一项。如果游戏不暴露攻击预警数据，可能需要降级方案——如使用空间音频持续播报周围敌人的位置变化（距离和方位），让玩家通过经验判断攻击时机。

### T2.3 受击/命中反馈增强

| 属性 | 内容 |
|---|---|
| **功能** | 玩家命中敌人时给予确认音效（区分普通命中/暴击/击杀）；玩家受击时播报受击方向和伤害程度；Boss 血量关键阈值（如 50%/25%）主动播报 |
| **当前状态** | ❌ 完全未实现 |
| **调研依据** | 研究报告第二通道原则——盲人无法通过血条视觉反馈判断输出是否有效 |
| **实现难度** | **中** — 命中/受击可通过伤害事件钩子检测（如果游戏暴露）；血量阈值需要持续监控敌人 HP |

### T2.4 战斗资源状态播报

| 属性 | 内容 |
|---|---|
| **功能** | 关键战斗资源变化时主动播报：棍势层数变化、法术冷却完成、变身可用/剩余时间、葫芦最后一次时警告、定身术/分身术等法术就绪 |
| **当前状态** | ❌ 完全未实现；`idea.md` 中提及"技能 CD 播报"和"变身形态状态播报" |
| **调研依据** | GoWR 的斯巴达之怒可通过触控板激活（提供替代反馈）；GAG Basic——关键状态变化不得仅通过视觉传达 |
| **实现难度** | **中** — 需要检测游戏状态变化事件（技能冷却计时器、棍势计数器等），取决于游戏暴露的数据 |

### T2.5 输入操作无障碍

| 属性 | 内容 |
|---|---|
| **功能** | 连按→长按替代；持续按住→切换替代；完全按键重映射（此项游戏本身已部分支持） |
| **当前状态** | ❌ 完全未实现 |
| **调研依据** | 研究报告 R1/R2（Intermediate 级，对盲人不变——操作无障碍与视力无关） |
| **实现难度** | **中** — 需要在输入层面做拦截和转换，技术上可行但需要深入了解 UE4 输入系统 |

## T3 — 探索能力（3 项）

> 不实现这些，盲人玩家无法自主移动和探索世界——没有视力导航，寸步难行。

### T3.1 声音地标导航系统

| 属性 | 内容 |
|---|---|
| **功能** | 在关键路径节点（土地庙、Boss 门口、关键 NPC、宝箱、可交互物体旁）放置声音地标 → 玩家靠近时听到对应方向的循环音效或周期性提示音 → 顺着声音导航到达目标 |
| **当前状态** | ⚠️ 完整设计文档已存在于 `docs/idea/sound_landmark_navigation.md`（Phase 1–4），但代码未开始 |
| **调研依据** | GoWR 的导航辅助通过音频提示描述环境并提供摇杆引导；Celeste 辅助模式提供路径引导；研究报告中 R6（任务日志——对盲人升级为主动音频引导） |
| **实现难度** | **高** — 设计文档已规划四阶段：Phase 1（单个目标 3D 音效定位）、Phase 2（路径点串联）、Phase 3（动态目标更新）、Phase 4（剧情/战斗中的上下文感知）。核心技术挑战：(1) 如何在 UE4 中放置/播放 3D 空间音频（可能通过 UE4SS 调用引擎音频 API）、(2) 如何获取关键位置的坐标数据、(3) 路径点之间的连通性判断 |

**设计文档**：`docs/idea/sound_landmark_navigation.md`

### T3.2 障碍物/地形边界检测与警告

| 属性 | 内容 |
|---|---|
| **功能** | 玩家接近悬崖/深渊边缘时发出警告音（距离越近越急促）；碰到不可通过的墙壁/障碍时播报方向和距离 |
| **当前状态** | ❌ 未实现，无设计文档 |
| **调研依据** | Another Crab's Treasure 阻止坠落伤害；GoWR 的边缘辅助防止跌落 |
| **实现难度** | **高** — 需要持续检测玩家前方地形（射线检测？NavMesh 边界？），在复杂地形中区分"可通行"和"会坠落" |

### T3.3 朝向与方向指引

| 属性 | 内容 |
|---|---|
| **功能** | 一键播报当前朝向（"面向北方"或"面向土地庙方向"）；向玩家提供前往目标的时钟方位指引（"土地庙在 2 点钟方向，约 30 米"） |
| **当前状态** | ❌ 未实现；`idea.md` 中提及"距怪物距离播报"和"朝向辅助" |
| **调研依据** | GoWR 的导航辅助在摇杆上施加力引导方向；Forza Motorsport 为盲人驾驶员提供音频方向提示 |
| **实现难度** | **低–中** — 技术上只需读取玩家位置和朝向（已有工具函数 `WkUtils`），以及目标位置，计算方位角和距离即可 |

## T4 — 完整体验（4 项）

> 不实现这些，盲人玩家可玩但不完整——错过剧情、无法高效管理装备、缺少社区连接。

### T4.1 过场动画音频描述

| 属性 | 内容 |
|---|---|
| **功能** | 在过场动画播放期间，通过 TTS 朗读关键视觉信息旁白（角色动作、场景变化、关键表情、字幕未覆盖的重要画面信息） |
| **当前状态** | ❌ 完全未实现 |
| **调研依据** | TLOU2 Remastered (2024) 新增剧情音频描述；研究报告 A7（Advanced 级） |
| **实现难度** | **很高** — 最具挑战性的功能之一。需要：(1) 为每段过场预编写音频描述脚本（人工创作，无法自动生成）、(2) 检测过场动画的播放进度以同步描述、(3) 在游戏音频的间隙中插入不重叠的 TTS 描述。对于 Mod 项目而言，编写全部过场的描述脚本工作量巨大 |

**现实考量**：对于 Mod 项目，完整覆盖所有过场动画可能不现实。建议**优先覆盖关键剧情节点**（开场、结局、关键转折），逐步扩展。

### T4.2 装备/技能管理辅助

| 属性 | 内容 |
|---|---|
| **功能** | 物品栏浏览时播报完整属性对比（当前装备 vs. 候选装备的数值差异）；技能树浏览时播报技能效果描述、消耗资源、前置条件 |
| **当前状态** | ⚠️ 部分实现 — 物品/装备/技能按钮已能朗读名称和基本等级，但缺少：属性数值对比、技能效果详细描述 |
| **调研依据** | 研究报告 R6 — 目标/任务日志（对盲人扩展为完整的菜单辅助决策）；`docs/idea/settings_menu_analysis.md` 设计了通过 `GameDBRuntime` 获取详细描述的方法 |
| **实现难度** | **中** — 核心挑战是读取物品属性数据和技能描述文本（可能存储在 DataTable 或配置数据库中），以及格式化属性对比播报 |

### T4.3 任务日志与目标回顾

| 属性 | 内容 |
|---|---|
| **功能** | 随时可回顾当前任务目标、已获取的 NPC 对话关键信息；播报任务进度 |
| **当前状态** | ❌ 完全未实现 |
| **调研依据** | 《艾尔登法环》缺少任务日志是残障玩家社区明确抱怨的痛点；研究报告 R6 |
| **实现难度** | **中** — 取决于游戏是否有任务日志 UI / 数据（黑神话悟空有旅程/游记系统，可能包含此类数据），与 T1.4 菜单朗读共享技术基础 |

### T4.4 音频自定义与混音

| 属性 | 内容 |
|---|---|
| **功能** | TTS 音量独立调节（不与游戏音效/音乐混在一起）；不同类别音频提示（战斗预警/导航指引/状态播报）可独立开关和调音量；3D 空间音频定位精度可调 |
| **当前状态** | ❌ 完全未实现 |
| **调研依据** | GoWR 的音频提示系统配有完整词汇表和独立音量调节；Forza Motorsport 提供详细的音频辅助自定义 |
| **实现难度** | **中** — 取决于音频输出架构。如果所有音频提示都通过 TTS 输出，则只需 TTS 音量控制；如果引入 3D 音效，则需独立的音频混合 |

## 关键设计原则（盲人专属）

### 1. "被动感知"优先于"主动查询"

盲人玩家无法看到屏幕上的变化。**任何关键信息变化应主动播报，而非等待玩家按键查询。**

- ✅ Boss 血量降至 50% → 主动播报
- ✅ 棍势升层 → 主动播报
- ✅ 锁定丢失 → 主动播报
- ❌ 需要按键才知道血量/棍势/锁定状态

**例外**：高频变化的信息（如玩家具体 HP 数值每秒变化多次），应提供两个级别：变化趋势主动简短提示（"血量偏低！"）+ 详细数值按键查询。

### 2. "分级播报"优于"全部播报"

音频通道是串行的（同一时间只能听一个声音），而视觉可以并行处理。盲人玩家面临的最大挑战是**音频信息过载**。

- **紧急级**（打断所有）：敌人即将攻击、血量危殆、坠落警告 → 短促紧急音效 + TTS
- **重要级**（排队播报）：场景切换、交互物品接近、技能冷却完成 → TTS 排队
- **信息级**（仅主动查询）：详细状态、地图位置、物品属性 → 按键触发 TTS

### 3. "空间音频"优先于"文字描述"

对于方向和位置信息，**3D 空间音效比 TTS 文字播报更高效**：
- "敌人在左边"：一个从左声道传来的周期性提示音 >> TTS 播报"敌人，左侧，3 米"
- 声音地标导航：循环音效从地标方向传来，玩家凭听觉即可转向导航
- 攻击方向预警：短促音效从攻击来向播放，比"注意，右侧攻击"更快更直观

TTS 应保留用于必须用语言表达的信息（名称、数值、状态描述）。

### 4. "降级可行"优于"完美方案"

对于技术可行性不确定的功能（特别是 T2.2 攻击预警），**先做能做的降级方案**，让玩家至少能"参与战斗"，而不是因为没有完美方案就什么都不做。

- 无法检测攻击预警？→ 持续播报敌人距离和方位变化（距离骤然缩短 + 特定方位 = 可能正在攻击）
- 无法读取 Boss 阶段转换？→ 播报 Boss 血量变化趋势（大幅下降后停滞 = 可能进入下一阶段）
- 无法知道攻击类型？→ 至少让玩家知道"有东西正在靠近"

## 风险与制约

1. **攻击预警的技术可行性（T2.2）**：这是整个清单中最不确定的一项。取决于 UE4 游戏引擎向 Mod 脚本暴露的攻击数据粒度。如果只能读取到"敌人存在"而无法读取"敌人即将攻击"，则需要完全依赖空间音频+距离变化推理。

2. **音频信息过载**：战斗场景中同时存在游戏原生音效、TTS 播报、空间音频提示——如何避免信息过载是重大设计挑战。需要严格的信息分级和播报节流机制。

3. **单人 Mod 开发资源有限**：T4.1 过场音频描述即使只覆盖关键剧情节点，也需要大量人工创作。T3.1 声音地标的 Phase 2-4 路径规划需要遍历游戏地图。

4. **Mod 的技术边界**：作为运行在 UE4SS 框架下的 C# Mod，某些功能可能受限于引擎暴露的数据和 API。所有"高"难度项都应在实际编码前做技术可行性 spike。
